# 観測記録 編集・添削基準ガイドライン (Editing Guidelines)

## 1. 目的と運用の全体像

本ドキュメントは、弘前市の現地直接観測アーカイブである「Hirosaki View（ヒロサキビュー）」において、**新規観測記録を既存アーカイブ（`observations/`）に自然に統合するための編集・添削基準**を定めたものです。

今後の観測運用体制：
1. **Gemini**: 現地観測情報（メモ・写真番号・日時・場所・一次所見など）に基づき、観測記録Markdownの下書き（ドラフト）を作成する。
2. **ChatGPT**: 本基準書および既存リポジトリを参照し、形式、メタデータ（Front Matter）、事実と解釈の分離、命名規則、内部リンク、文章表現を添削・補正する。
3. **GitHub Auto-Register**: 添削後の完成Markdownを人間がGitHub Issue等を通じて `observations/` ディレクトリに登録する。

添削者（ChatGPT）の最重要の役割は、**「新しい理想的なフォーマットを勝手に考案すること」ではなく、「既存アーカイブの住人（実データ）と同じ形式・品質・関係性を持つ形に整えること」**です。

## 2. ファイル命名規則と観測ID (`id`)

観測ファイルはリポジトリの `observations/` ディレクトリ直下に配置されます。

### 2-1. ファイル命名規則
基本フォーマット：
```text
observations/YYYYMMDD-[location-or-series-slug].md
```
- **日付部 (`YYYYMMDD`)**: 観測実施日をハイフンなしの8桁西暦（例: `20260917`）で表記します。
  - ※注意: 過去に `2026-11-03-...` や `2026-11-05-...` のようなハイフン入りファイル名が一時的に作成された履歴がありますが、標準の正規規則は**ハイフンなし8桁**（`2026MMDD`）です。
- **スラッグ部 (`slug`)**: 半角小文字英数字とハイフンのみを使用します。
  - 地点名、またはイベント/シリーズ名を表す簡潔な英語識別子にします。
  - 例: `apple-music-fes-setup.md`, `hirosaki-park.md`, `station-to-otemon.md`, `botanical-garden-inner-area-summary.md`

### 2-2. 観測ID (`id`) の生成規則
Front Matter 内の `id` は、**ファイル名（拡張子 `.md` を除く）の先頭に `hv-` を付与したもの**と完全一致させます。

- ファイル名が `20260917-apple-music-fes-setup.md` の場合：
  `id: hv-20260917-apple-music-fes-setup`
- ファイル名が `20261106-otemon-outer-area-summary.md` の場合：
  `id: hv-20261106-otemon-outer-area-summary`

## 3. Front Matter (メタデータ) 記述ルール

観測Markdownの冒頭には、必ずYAML形式の Front Matter を配置します。

```yaml
---
id: hv-20260917-apple-music-fes-setup
date: 2026-09-17
location: apple-park
title: "弘前市りんご公園・りんごミュージックフェス関連設置物観測（設営状態：2026-09-17）"
series: apple-music-fes
type: event-setup
observer: Hirosaki-View
direct_observation: true
prev_observation: 20260914-apple-music-fes-normal.md
next_observation: 20260919-apple-music-fes-holding.md
---
```

### 3-1. フィールド一覧と仕様

| フィールド名 | 必須 | 型 | 説明 | 許容値 / 記述例 |
| :--- | :---: | :--- | :--- | :--- |
| `id` | **必須** | String | 観測記録の一意識別子 | `hv-YYYYMMDD-slug` |
| `date` | **必須** | Date | 観測実施日（ISO 8601形式） | `2026-09-17` |
| `location` | **必須** | String | 観測地点識別子（小文字ケバブケース） | `apple-park`, `hirosaki-park`, `hirosaki-park-otemon`, `station-to-otemon`, `iwakisan-jinja`, `aomoriken-budokan` |
| `title` | **必須** | String | 観測記録の正式タイトル（ダブルクォート推奨） | `"弘前市りんご公園・りんごミュージックフェス関連設置物観測（設営状態：2026-09-17）"` |
| `series` | 任意 | String | 関連する観測シリーズ識別子 | `apple-music-fes`, `shirofes`, `hirosaki-park-2026`, `apple-park-2026`, `urban-routes`, `hirosaki-castle-chrysanthemum-and-autumn-foliage-festival-2026` |
| `type` | **必須** | String | 観測種別（後述の規定値） | `fixed-point`, `route`, `event-setup`, `event-holding`, `event-teardown`, `event-time-series-summary` |
| `observer` | **必須** | String | 観測実施者名 | 原則 `Hirosaki-View` |
| `direct_observation` | **必須** | Boolean | 現地直接観測であるか | 単一観測や現地直接観測は `true`。複数観測を統合したサマリー等の場合は `false` または `true`（現地の直接観測に基づく統合） |
| `period` | 任意 | String | 観測期間（統合記録などで期間を持つ場合） | `2026-10-30T08:21:00+09:00 - 2026-11-05T08:22:00+09:00` |
| `prev_observation` | 任意 | String | シリーズ内の1つ前の観測ファイル名 | `20260914-apple-music-fes-normal.md` |
| `next_observation` | 任意 | String | シリーズ内の1つ後の観測ファイル名 | `20260919-apple-music-fes-holding.md` |

## 4. 観測本文の標準構成と記録種別ごとのテンプレート

本文構造は、自動監査プログラム（`AUDIT_PROGRAM.yml`）およびAI可読性の観点から、共通する標準見出しを基本骨格とします。

### 4-1. 必須見出し（機械監査チェック対象）
本文中には以下の3つの語句が明示的に含まれている必要があります。
- **`観測日時`**
- **`場所`**
- **`観測対象`**

通常、これらは「`## 観測概要`」の直下の箇条書きで定義されます。

```markdown
# [観測タイトル]

## 観測概要
- **観測日時**: 2026-09-17 11:30〜12:15（または 2026-09-17）
- **場所**: 弘前市りんご公園「りんごの家」前グラウンド
- **観測対象**: りんごミュージックフェス2026 仮設ステージ・音響テント等の設営物
```

---

### 4-2. 記録種別ごとの構成ガイド

Hirosaki View では、観測対象の性質に応じて5つの主要パターンが存在します。すべてを無理やり画一化せず、各パターンの特徴を尊重してください。

#### パターンA: 単一地点・イベントフェーズ定点観測 (`event-setup`, `event-holding`, `event-teardown`, `fixed-point`)
- **代表例**: `observations/20260914-apple-music-fes-normal.md`, `20260917-apple-music-fes-setup.md`
- **特徴**: イベント等の設営・開催・撤収プロセスや定点での状態変化を克明に追跡する標準形式。
- **推奨構成**:
  1. `# タイトル`
  2. `## 観測概要`（観測日時、場所、観測対象）
  3. `## 観測事実 (Observation)`（現地で視覚的に確認された物理的事実を箇条書き）
  4. `## 空間的変容 (Change / Transition)`（前回観測からの変化、出現、消失、原状回復）
  5. `## Human observation / 解釈`（観測者の定性的所見、空間文脈、解釈）
  6. `## Evidence`（撮影写真番号等）
  7. `## 観測間ナビゲーション / 関連リンク`（前後の観測、シリーズ一覧へのリンク）

#### パターンB: 移動経路・都市横断ルート観測 (`route`)
- **代表例**: `observations/20260819-station-kajimachi.md`, `20260915-station-to-otemon.md`
- **特徴**: 駅から中心市街地、公園等へ移動しながら連続的に複数の定点（ウェイポイント）を観測する。
- **推奨構成**:
  1. `# タイトル`
  2. `## 観測概要`（観測日時、ルート全体、観測対象）
  3. `## 観測ログ一覧` または `## 各観測地点の記録`
     - `### [地点番号 / 地点名]`（例: `### HP-002: 弘前駅前モニュメント`）
     - 観測時刻、場所、観測対象、観測事実、Evidence
  4. `## ルート全体の総括 / 変容`
  5. `## 観測間ナビゲーション / 関連リンク`

#### パターンC: 単一イベント・複数地点同時観測 / エリア総合観測 (`fixed-point` または `event-*`)
- **代表例**: `observations/20261106-otemon-outer-area-summary.md`, `20261106-botanical-garden-inner-area-summary.md`
- **特徴**: 祭りやイベントの特定日に、会場内外の複数サブエリア（アプローチ、広場、庭園など）を一括して観測・記録する。
- **推奨構成**:
  1. `# タイトル`
  2. `## 観測概要`（観測日時範囲、広域場所、観測対象リスト）
  3. `## 観測事実 (Observation)`
     - サブエリアごとの小見出し（`### 1. 追手門前アプローチ（15:30 - 15:31）` など）
  4. `## 空間的変容 (Change / Transition)`
  5. `## Human observation / 解釈`
  6. `## Evidence`
  7. `## 観測間ナビゲーション / 関連リンク`

#### パターンD: 時系列統合記録 (`event-time-series-summary`)
- **代表例**: `observations/2026-11-05-applepark-harvest-festival-summary.md` の本文構成
- **特徴**: 一連のイベント（設営〜開催〜撤収）における複数の個別観測時点を1つの記録に統合し、時系列の推移・変化・未確認事項を総括する。
- **推奨構成**:
  1. `# タイトル`
  2. `## 観測概要`（対象期間、場所、対象イベント）
  3. `## 1. 観測目的`
  4. `## 2. 背景情報・公式情報`（公式発表日程や概要。※現地観測事実とは峻別）
  5. `## 3. 各時点の個別観測記録`（観測ID、日時、天候、各時点の観測事実）
  6. `## 4. 空間状態の時系列変化`（設備変化、環境変化）
  7. `## 5. 比較上の注目点`
  8. `## 6. 推知・解釈`
  9. `## 7. 未確認事項`
  10. `## 8. 一次データトレーサビリティ`（画像番号と観測IDの対応）
  11. `## 観測間ナビゲーション / 関連リンク`

## 5. 観測事実と解釈・推測の厳格な分離

添削者が最も厳しくチェックすべき規範です。

1. **直接観測事実 (Observation)**
   - 観測者が現地で物理的・視覚的に確認したことのみを記述します。
   - 良い例: `「白色のパイプテントが3棟設営されており、骨組みに紅白幕が取り付けられている。」`
   - 悪い例: `「明日の開会式に向けて関係者が準備を進めている。」`（「明日の開会式に向けて」は推測・背景情報であり、事実ではない）
2. **空間的変容 (Change / Transition)**
   - 前回観測または平常時と比較して、物理的に何が出現し、何が消失・変化したかを記述します。
3. **解釈・推知 (Human observation / Interpretation)**
   - 観測事実から推論される空間の機能や文脈は、必ず「解釈」または「推知」セクションに記述します。
   - 表現の末尾は「〜と考えられる」「〜と推測される」「〜の可能性がある」を用います。
4. **公式情報の扱い**
   - 主催者告知や行政広報は「背景情報」として扱い、現地観測事実を補完・改変する根拠として用いてはなりません。

## 6. 情報不足・未確認事項の取り扱い

- **推測による補完の禁止**: 観測データに存在しない日時、正確な撤収完了時刻、資材の仕様、天候の詳細などを、AIが推測や一般知識で「埋める」ことは固く禁止します。
- **未確認事項の明示**: 不明な点や確認できなかった空白期間は、隠さず「`## 未確認事項 (Unconfirmed Items)`」に箇条書きで明記してください。
  - 例: `「11月2日から11月5日までの間の撤去作業の進行過程は未観測。」`

## 7. 関連記録の検索・参照リンク作成ルール

### 7-1. 相対パスの指定
観測Markdown（`observations/` 直下のファイル）同士のリンクは、同一ディレクトリ内であれば相対ファイル名で指定します。
- 良い記述例（観測ファイル内からの指定）: `[通常状態]` に `20260914-apple-music-fes-normal.md` への相対リンクを張る
- 良い記述例（観測ファイル内からの指定）: `[総合インデックス]` に `index.md` への相対リンクを張る
- 誤った記述例: `[通常状態]` に `../observations/20260914-apple-music-fes-normal.md` のような同一階層での不要な `../` を付けたリンクを張る
- 誤った記述例: 存在しないファイルへのデッドリンク

### 7-2. 実在するファイルの照合
リンクを生成する際は、リポジトリに実在する観測ファイルを `observations/index.md` やファイル一覧で確認し、正確なリンク先を指定してください。まだ作成されていない個別記録を参照する場合は、リンク記法（`[...]`）にせずインラインコード（` `hv-xxxx` `）として表記します。

### 7-3. 不要なクリーンアップ（禁止事項）
LLMの生成物に時折混入する `[span_0](start_span)` や `[span_1](end_span)` などの内部参照用タグは、リンク切れエラーの原因となるため、添削時に**完全に除去**してください。

## 8. ChatGPT添削チェックリスト

Gemini作成の下書きを受け取ったら、ChatGPTは以下のチェックリストに沿って添削を行ってください。

- [ ] **ファイル名**: `YYYYMMDD-[slug].md` の命名規則に従っているか？
- [ ] **Front Matter**: 必須フィールド（`id`, `date`, `location`, `title`, `type`, `observer`, `direct_observation`）が揃っているか？
- [ ] **観測ID**: `id: hv-[slug]` がファイル名と一致しているか？
- [ ] **必須キーワード**: 本文中に「`観測日時`」「`場所`」「`観測対象`」の3項目が含まれているか？
- [ ] **事実と解釈の分離**: 「観測事実」の欄に主観的な憶測やイベント概要が混ざっていないか？
- [ ] **未確認事項の明示**: 不明な情報を推測で捏造・補完していないか？
- [ ] **リンク整合性**: 本文内の内部リンク先ファイルが実在しているか？（`start_span` 等のゴミ記法が混入していないか？）
- [ ] **Evidence**: 写真番号や検証証拠が正しく紐付いているか？
