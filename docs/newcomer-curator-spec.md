# 新規データ受け入れ・ブラッシュアップAI（将来構想）

> **位置づけ**: 本文書は、将来的に観測データの受け入れ・ブラッシュアップを自律的・半自動的に行うAI機構の**設計構想資料（未実装・将来検討構想）**です。
> 現在の実運用体制（現行機能）と将来構想を明確に区別して記載しています。

## 1. 目的

新しい観測データを投入すると、AIがHirosaki Viewの既存ファイル、命名規則、データ仕様、関連記録を調査し、既存リポジトリの構造に適合した登録候補へ整える。

目的はリポジトリ全体を定期的に掃除することではない。

新しいデータを既存の住人と同じ規則・構造・関係性を持つ形に整え、リポジトリへ自然に受け入れることを目的とする。

## 2. 現行運用と将来構想の区別

### 2-1. 現行の確定運用体制（実装済み）
現在稼働している運用フローは以下のとおりです。
1. **Gemini**: 現地観測情報（メモ・写真番号・日時・場所・一次所見など）に基づき、観測記録Markdownの下書き（ドラフト）を作成する。
2. **ChatGPT**: 既存リポジトリの実データ、規則（`docs/editing-guidelines.md` 等）、関連記録と照合して添削・補正する。
3. **人間確認と登録**: 人間が内容を確認し、GitHub Register（入力支援・登録ツール）等を通じて登録する。

※過去に存在したGitHub ActionsによるIssue本文からの自動登録（`auto-register-observation.yml`）や、特定AIエージェント（Jules等）による自動PR作成への永続依存は廃止・終了しており、現在は人間主導による確認・登録を基本運用としています。

### 2-2. 将来のAI受け入れ構想（未実装）
将来構想として、上記の添削・適合・PR作成プロセスをさらに統合・自動補助する仕組みを検討しています。
1. 利用者が新しい観測データを投入する。
2. 受け入れAIが既存の規範文書、類似記録、関連記録を調査する。
3. 命名規則、配置先、Front Matter、本文構造を確認する。
4. 関連リンクや必要なメタデータを補完する。
5. 元データとの照合により、情報欠落、事実改変、重複を検査する。
6. 完成候補と判断が必要な事項を利用者に提示する。
7. 利用者の承認後、専用ブランチとPull Requestを作成する。
8. 既存の機械監査を実行し、検査結果を報告する。

## 3. リポジトリ内機能との役割分担

### 機械監査装置（実装済み・維持）

`.github/workflows/AUDIT_PROGRAM.yml`

mainへのPush時または手動実行により、以下の項目を検査する。

- パスに含まれる不審な文字やUnicode文字
- Markdown内のローカルリンク
- ファイルパスの参照関係
- 観測ファイルの基本項目
- RSS・Atomの生成と観測データとの同期

### プロジェクト資料（実装済み）

- `docs/purpose.md`：プロジェクトの目的と基本思想
- `docs/dataset-specification.md`：データ構造と記述規約
- `docs/editing-guidelines.md`：観測記録の編集・添削基準
- `llms.txt`：AI向けのプロジェクト案内と主要参照先
- `observations/`：一次観測データの正本

### 将来受け入れAI構想の担当範囲（未実装）

将来の受け入れAIは、既存データの意味理解、類似記録の発見、命名・配置・記述形式の適合、関連情報の接続を担当する構想である。

既存の機械監査装置は置き換えず、AIが生成した登録候補の検査にも再利用する方針とする。

## 4. データ保全原則

新しいデータを既存構造に適合させる際は、以下の原則を守る。

- 直接観測された事実を、AIの推論や解釈によって書き換えない。
- 推論や解釈は禁止しない。ただし、直接観測された事実とは明確に区別する。
- 提供されていない日時、場所、座標、観測内容などを捏造しない。
- 不明な情報は推測で埋めず、未確認事項として残す。
- 既存記録を無断で変更・削除しない。
- 既存の命名規則は、実際のファイルや運用履歴を確認して適用する。
- 一般的な表記との違いだけを理由に、既存のファイル名やパスを変更しない。
- 公式情報は背景情報として扱い、現地観測の証拠の代わりにしない。
- 観測されていない期間を、連続して確認された事実として扱わない。
- 既存ファイルの上書きや重複登録を防止する。

## 5. 既存リポジトリの調査方法

AIは新しいデータを処理する前に、既存リポジトリを調査する。

参照対象は以下のとおり。

1. `docs/purpose.md`
2. `docs/dataset-specification.md`
3. `llms.txt`
4. `observations/` 内の類似・関連記録
5. 既存のワークフローと監査プログラム
6. 必要に応じて過去の変更履歴

特に、類似する場所・観測対象・イベント・時系列記録を探し、既存データとの関係を確認する。

仕様書と既存の実例に差異がある場合、AIは一方を勝手に正解と決めず、その差異を報告する。

既存の住人を理解したうえで、新しい住人に適用する規則を判断する。

## 6. 新規データのブラッシュアップ

AIは、新規データに対して以下の処理を行う。

### 6-1. 配置と命名

- 適切な保存先ディレクトリを判断する。
- 既存のファイル命名規則を踏襲する。
- 既存ファイルとの重複を確認する。
- 必要に応じて適切なファイル名を提案する。

### 6-2. データ構造の適合

- 既存仕様に沿ったFront Matterを生成する。
- 必要な見出し構造を整える。
- Markdownの表、リンク、リストなどを正しい形式にする。
- 既存記録と共通する項目の記述形式を揃える。

### 6-3. 関連情報の接続

- 関連する過去の観測記録を探す。
- 実在するファイルパスを確認してリンクを生成する。
- 時系列上の前後関係を確認する。
- 関連する観測シリーズや場所との関係を整理する。

### 6-4. 内容の整理

- 元データの情報を保持する。
- 重複した記述を整理する。
- 観測事実と推論・解釈を分離する。
- 比較に役立つ情報を構造化する。
- 不足情報や未確認事項を明示する。

## 8. MVPの実装範囲（構想検討）

最初の実装では、以下の機能に限定する。

- 新規データを投入できる入口を用意する。
- 既存の規範文書と関連記録を自動取得する。
- AIが既存構造に適合した登録候補を生成する。
- 元データと生成結果の差異を確認する。
- 情報欠落、事実改変、重複、リンク、書式を検査する。
- 完成候補と判断が必要な事項を提示する。
- 承認前に `main` へ直接書き込まない。
- 承認後は専用ブランチとPull Requestを使用する。
- 既存の機械監査を再利用する。

初期段階では、既存ファイルの一括改修や無人マージは行わない。

## 9. AIモデルとの接続

GitHub ActionsからAIモデルを自動的に呼び出すには、モデル/APIとの接続と認証情報の設定が必要となる。

現時点では以下を未決定事項とする。

- AIプロバイダーと使用モデル
- APIまたは外部エージェントとの接続方法
- GitHub Actions Secrets等への認証情報の登録
- API利用料金、無料枠、利用制限
- 画像入力への対応方法

これらを確認せず、既存のAI接続が利用できると仮定して実装しない。

## 10. 最初の受け入れテスト

初回のテスト対象として、以下の既存ファイルを使用する。

`observations/2026-11-05-applepark-harvest-festival-summary.md`

このファイルを使い、以下を検証する。

1. 登録指示文と成果物本文を分離できるか。
2. Front Matterを既存仕様に沿って生成できるか。
3. Markdownの見出し・表・リンクを正しく整形できるか。
4. 既存の個別観測記録を発見し、正しいリンクを生成できるか。
5. `applepark` など既存の命名規則を保持できるか。
6. 観測事実と推論・解釈を区別できるか。
7. 元データに存在しない情報を追加していないか。
8. 既存ファイルを変更せず、差分として修正案を生成できるか。
9. 完成候補を既存の機械監査に通せるか。

## 11. 完了条件（将来構想の達成目標）

以下を満たした場合、MVPの完成とする。

- 新しいデータを一度投入するだけで、AIが既存リポジトリの構造を調査できる。
- 既存の命名・記述規則に適合した登録候補を生成できる。
- 関連する既存記録を発見し、適切な参照関係を作れる。
- 元データの事実を保持し、推論は区別して追加できる。
- 不明な情報を捏造せず、要確認事項として提示できる。
- 利用者が毎回、既存ファイルの場所・命名規則・書式・関連記録を手作業で調べ直す必要がない。
- 承認後にPull Requestを作成し、既存の機械監査で検査できる。

最終的な利用者の操作は、

**新しいデータを投入する → 完成候補を確認する → 承認する**

という簡単な流れを目指す。
