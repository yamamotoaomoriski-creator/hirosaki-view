# 新規データ受け入れ・ブラッシュアップAI

## 1. 目的

新しい観測データを投入すると、AIがHirosaki Viewの既存ファイル、命名規則、データ仕様、関連記録を調査し、既存リポジトリの構造に適合した登録候補へ整える。

目的はリポジトリ全体を定期的に掃除することではない。

新しいデータを既存の住人と同じ規則・構造・関係性を持つ形に整え、リポジトリへ自然に受け入れることを目的とする。

## 2. 基本動作

1. 利用者が新しい観測データを投入する。
2. AIが既存の規範文書、類似記録、関連記録を調査する。
3. 命名規則、配置先、Front Matter、本文構造を確認する。
4. 関連リンクや必要なメタデータを補完する。
5. 元データとの照合により、情報欠落、事実改変、重複を検査する。
6. 完成候補と判断が必要な事項を利用者に提示する。
7. 利用者の承認後、専用ブランチとPull Requestを作成する。
8. 既存の機械監査を実行し、検査結果を報告する。

## 3. 既存機能との役割分担

Hirosaki Viewには、すでに以下の仕組みが存在する。

### 既存の自動登録装置

`.github/workflows/auto-register-observation.yml`

GitHub Issueに `register-md` ラベルが付くと起動し、Issueタイトルをファイルパス、Issue本文をMarkdown本文としてリポジトリに登録する。

### 既存の機械監査装置

`.github/workflows/AUDIT_PROGRAM.yml`

Push時または手動実行により、以下の項目を検査する。

- パスに含まれる不審な文字やUnicode文字
- Markdown内のローカルリンク
- ファイルパスの参照関係
- 観測ファイルの基本項目
- RSS・Atomの生成と観測データとの同期

### 既存のプロジェクト資料

- `docs/purpose.md`：プロジェクトの目的と基本思想
- `docs/dataset-specification.md`：データ構造と記述規約
- `llms.txt`：AI向けのプロジェクト案内と主要参照先
- `observations/`：一次観測データの正本

### 新機能の担当範囲

新しいAIは、既存データの意味理解、類似記録の発見、命名・配置・記述形式の適合、関連情報の接続を担当する。

既存の機械監査装置は置き換えず、AIが生成した登録候補の検査にも再利用する。

## 4. データ保全原則

新しいデータを既存構造に適合させる際は、以下の原則を守る。

- 直接観測された事実を、AIの推論や解釈によって書き換えない。
- 推論や解釈は禁止しない。ただし、直接観測された事実とは明確に区別する。
- 提供されていない日時、場所、座標、観測内容などを捏造しない。
- 不明な情報は推測で埋めず、未確認事項として残す。
- 既存記録を無断で変更・削除しない。
- 既存の命名規則は、実際のファイルや運用履歴を確認して適用する。
- 一般的な表記との違いだけを理由に、既存のファイル名やパスを変更しない。
- 公式情報は背景情報として扱い、現地観測の証拠の代わりにしない。
- 観測されていない期間を、連続して確認された事実として扱わない。
- 既存ファイルの上書きや重複登録を防止する。

## 5. 既存リポジトリの調査方法

AIは新しいデータを処理する前に、既存リポジトリを調査する。

参照対象は以下のとおり。

1. `docs/purpose.md`
2. `docs/dataset-specification.md`
3. `llms.txt`
4. `observations/` 内の類似・関連記録
5. 既存のワークフローと監査プログラム
6. 必要に応じて過去の変更履歴

特に、類似する場所・観測対象・イベント・時系列記録を探し、既存データとの関係を確認する。

仕様書と既存の実例に差異がある場合、AIは一方を勝手に正解と決めず、その差異を報告する。

既存の住人を理解したうえで、新しい住人に適用する規則を判断する。

## 6. 新規データのブラッシュアップ

AIは、新規データに対して以下の処理を行う。

### 6-1. 配置と命名

- 適切な保存先ディレクトリを判断する。
- 既存のファイル命名規則を踏襲する。
- 既存ファイルとの重複を確認する。
- 必要に応じて適切なファイル名を提案する。

### 6-2. データ構造の適合

- 既存仕様に沿ったFront Matterを生成する。
- 必要な見出し構造を整える。
- Markdownの表、リンク、リストなどを正しい形式にする。
- 既存記録と共通する項目の記述形式を揃える。

### 6-3. 関連情報の接続

- 関連する過去の観測記録を探す。
- 実在するファイルパスを確認してリンクを生成する。
- 時系列上の前後関係を確認する。
- 関連する観測シリーズや場所との関係を整理する。

### 6-4. 内容の整理

- 元データの情報を保持する。
- 重複した記述を整理する。
- 観測事実と推論・解釈を分離する。
- 比較に役立つ情報を構造化する。
- 不足情報や未確認事項を明示する。

## 7. 処理フロー

新規データ投入

↓

既存リポジトリの調査

↓

類似記録・命名規則・データ仕様の把握

↓

新規データのブラッシュアップ

↓

事実保持・情報欠落・重複・参照関係の検査

↓

完成候補と要確認事項を提示

↓

利用者による承認

↓

専用ブランチに登録候補を反映

↓

Pull Request作成

↓

既存の機械監査による再検査

↓

最終確認・マージ

## 8. 役割分担とMVPの実装範囲

本基盤は、開発を担当したJulesに依存せず、Jules運用終了後（2026年11月11日以降）も人間・汎用LLM・GitHub Actionsの3者が協調して永続的に自律運用できるように役割を明確に分離しています。

### 役割分担
1. **人間 (Human)**:
   - 新規観測データを投入する（Issueテンプレート `.github/ISSUE_TEMPLATE/new-observation-curation.md`）。
   - LLMが作成した登録候補Markdownを確認・承認する。
   - PRを作成・確認し、`main` への最終マージを承認する。
2. **汎用LLM (ChatGPT, Gemini, Claude等)**:
   - 既存仕様書（`docs/dataset-specification.md`, `llms.txt`, `observations/index.md`）と類似記録を調査する。
   - 保存先、ファイル名、Front Matter、本文構造を判断する。
   - 直接観測事実と推知・解釈を厳格に分離する。
   - 関連記録・画像・時系列の接続候補を整理し、登録候補Markdownを作成する。
   - 不明点・未確認事項を明示する。
   - ※特定AIや有料APIに依存せず、人間が利用可能な任意のLLMで実行可能。
3. **GitHub Actions (機械検査基盤)**:
   - 機械的に判定できる形式・構造・リンク・ID重複を検査する（`scripts/validate_observation.py` および `AUDIT_PROGRAM.yml`）。
   - Pull Request段階で監査結果を表示し、不正データの混入を自動防止する。

### 今回のMVP（実装済み）
- **Issue投入テンプレート**: `.github/ISSUE_TEMPLATE/new-observation-curation.md` による未整理データの投入受付。
- **キュレーション手順の標準化**: 人間と汎用LLMによる調査・登録候補作成・ブランチ作成手順の確立。
- **機械検査バリデーター**: `scripts/validate_observation.py` による Front Matter・必須項目・ID重複・内部リンク等の機械的検査。
- **PR段階の自動監査**: `.github/workflows/AUDIT_PROGRAM.yml` の PR トリガー対応とバリデーター統合。
- **登録前検査**: `.github/workflows/auto-register-observation.yml`（既存 `register-md` 運用）における事前構文検査。

### 将来構想（未実装・将来拡張）
- 外部AI API（OpenAI, Anthropic, Google等）との自動接続およびActions内自動実行。
- 自動画像理解・マルチモーダル解析による写真メタデータ抽出。
- 高度な意味検索（ベクトル検索）による類似観測ログの自動サジェスト。
- 複数AIによる自動相互照合・相互レビュー。
- 完全無人登録・自動マージ（現在は人間の承認を必須とする安全設計）。

※未実装の将来構想を実装済みとして扱わず、外部APIキーや課金サービスの導入は行いません。

## 10. 最初の受け入れテスト

初回のテスト対象として、以下の既存ファイルを使用する。

`observations/2026-11-05-applepark-harvest-festival-summary.md`

このファイルを使い、以下を検証する。

1. 登録指示文と成果物本文を分離できるか。
2. Front Matterを既存仕様に沿って生成できるか。
3. Markdownの見出し・表・リンクを正しく整形できるか。
4. 既存の個別観測記録を発見し、正しいリンクを生成できるか。
5. `applepark` など既存の命名規則を保持できるか。
6. 観測事実と推論・解釈を区別できるか。
7. 元データに存在しない情報を追加していないか。
8. 既存ファイルを変更せず、差分として修正案を生成できるか。
9. 完成候補を既存の機械監査に通せるか。

## 11. 完了条件

以下を満たした場合、MVPの完成とする。

- 新しいデータを一度投入するだけで、AIが既存リポジトリの構造を調査できる。
- 既存の命名・記述規則に適合した登録候補を生成できる。
- 関連する既存記録を発見し、適切な参照関係を作れる。
- 元データの事実を保持し、推論は区別して追加できる。
- 不明な情報を捏造せず、要確認事項として提示できる。
- 利用者が毎回、既存ファイルの場所・命名規則・書式・関連記録を手作業で調べ直す必要がない。
- 承認後にPull Requestを作成し、既存の機械監査で検査できる。

最終的な利用者の操作は、

**新しいデータを投入する → 完成候補を確認する → 承認する**

という簡単な流れを目指す。
